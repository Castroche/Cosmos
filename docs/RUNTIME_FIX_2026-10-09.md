# 2026-10-09 卡顿与自动交易修复

原账户服务已恢复到 `http://127.0.0.1:8000`，自动化为 `OKX_DEMO / RUNNING`，覆盖 BTC、ETH、SOL，连续失败为 0，风险未暂停。当前策略处于等待状态，没有为了验收强制创建订单。

## 已定位的原因和修改

1. **离线审核反复解析大型历史证据。** 运行栈采样显示后台每 5 秒调用 `list_strategy_candidates`，解析并逐字符串修复 275 条旧策略的完整回测内容。数据库原始内容约 79 MB，解码结果约 85 MB，单次实测耗时 4.879 秒；这些记录均没有新版 `research_context`，最终全部跳过。新增专用轮询查询，旧记录只返回 ID，新版候选仍返回完整内容并按原合约校验。历史记录、计数和审计证据保留。相同数据库实测查询耗时 0.362 秒，解码结果降为 10,542 字符。
2. **数据库长任务阻塞交易共用锁。** 原备份和完整检查在约 7.8 GB 数据库操作期间持有应用锁；HTTP 和行情流程中的同步读写也在事件循环上等待。备份/检查改用独立且显式关闭的连接，备份分批复制；配置、风险和单个运行状态读取使用 WAL 快照，不等待应用写锁。K 线读写、价格唤醒、指标计算及目录构建移到后台线程。写事务、FULL 同步模式、版本检查与交易账户串行锁保留。SQLite 在线备份机制参考[官方说明](https://www.sqlite.org/backup.html)。
3. **模型加载阶段创建大量原生线程。** 预测已有单线程限制，但 LightGBM 从模型字符串加载时仍使用 OpenMP 默认线程数；观察到 API 进程达到 151 个线程。加载阶段也限制为一个 OpenMP 线程，并在结束后恢复原线程设置。并发加载只创建一个模型实例；总览只读元数据，不加载预测器。独立实测首次加载含依赖导入约 0.98 秒，另外两个模型各约 0.05 秒。
4. **启动接口等待 AI 决策导致超时。** 原启动/服务恢复流程在完成账户恢复后继续等待逐品种 AI 决策及符号锁，复现超过 120 秒后客户端超时，但后台其实已经启用。启动现在完成账户对账和待提交计划恢复后返回，新的决策由既有行情及队列后台任务继续处理。最新模拟盘启动包含账户验收耗时 6.717 秒，HTTP 200。停止代次、风险暂停及配置竞态检查保留。
5. **生成的有效价格区间已经不允许当前价格提交。** 多笔限价计划生成时价格就位于有效区间外，随后被执行层拒绝。生成合约及提示现在要求有效区间包含当前价格和委托价格，不合格输出进入原有的一次修正；真正无效的策略应等待。执行前与挂单期间的价格校验仍保留，价格在决策后离开区间仍拒绝/撤单。
6. **活动等待被历史数量上限遗漏。** 原查询先取最近 1,000 个等待记录，再按品种与状态筛选；大量已结束记录可能挤掉仍有效的等待条件。现在 SQL 先筛选品种和 ACTIVE，活动等待不受历史数量截断。空账户对账也不再每秒解析 5,000 个完整决策，仅在存在交易所挂单时读取订单归属证据。

排查开始时管理进程已不存在，8000 端口没有监听；残留状态文件记录的是旧进程。现有日志没有记录退出异常，无法从这些证据确定之前退出的原因。已通过现有管理启动器恢复原数据目录，保留账户配置和历史数据。
